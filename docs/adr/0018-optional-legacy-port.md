# ADR 0018: 互換用 AtomVM ポートを構築時に任意化する

## 状態

採用

## 背景

ADR 0017 で、LovyanGFX 装置適合層を直接呼び出す `LGFX` NIF API を追加した。
ESP32-S3 実機では、120個の矩形を個別に描画する直接 NIF が同等のポート呼び出しより
約2.7倍速く、事前に符号化した NIF バッチはさらに低負荷だった。

一方、既存の `AtomLGFX` ポート API には、最初の NIF 範囲にまだ含まれない機能がある。

- 実行時の詳細なパネル・バス設定
- スプライトの生成と解放、パレット
- タッチと較正
- JPEG
- 高度な文字、切り抜き、機能・診断情報

NIF を主経路とするファームウェアに、これらの組プロトコル解析器とハンドラーを常に
リンクする必要はない。しかし、機能差が残る間にポート実装そのものを削除すると、
既存アプリケーションと機器構成を移行できなくなる。

## 判断

直接 NIF を独立した翻訳単位として常に構築し、互換用ポートを CMake 設定
`LGFX_PORT_ENABLE_LEGACY_PORT` で任意化する。

- 既定値は移行中の互換性を保つため `ON` とする
- `OFF` ではポート入口、組プロトコル解析器、操作表、通常ハンドラーを構築しない
- `OFF` でも NIF、`lgfx_device` 装置適合層、バイナリーバッチ振り分けは構築する
- NIF とポートが共有する描画処理を複製しない
- NIF が必要な機能を十分に覆い、利用側の移行が完了するまではポートソースを削除しない

NIF だけのファームウェアは次のように構築する。

```bash
./scripts/atomvm_esp32.exs build --target esp32s3 --component . \
  --cmake-define LGFX_PORT_ENABLE_LEGACY_PORT=OFF
```

## 理由

NIF は、単純な同期描画に対して境界が薄く、API と実装を読みやすく保てる。
同じ命令列を繰り返す場合は、事前符号化したバイナリーバッチも再利用できる。
任意のポート構築は、この主経路を小さくしながら、まだ必要な機能の互換経路を保つ。

接続した ESP32-S3 の完全なファームウェア構築では、ポートを除外することで画像が
1,788,240 バイトから 1,744,560 バイトになり、43,680 バイト減少した。最小アプリ
領域の空きは 46,768 バイトから 90,448 バイトへ増えた。

## 影響

### 良い影響

- NIF だけを使う製品では、不要なポートコードと約43 KBのフラッシュ使用を避けられる
- NIF とポートの構築境界がソース単位で明確になる
- 既存利用者は既定設定を変えずに移行を続けられる
- NIF とポートは引き続き同じ装置処理とバッチ実行系を使う

### 悪い影響

- 移行中は2つのネイティブ構築構成を検証する必要がある
- `OFF` のファームウェアでは `AtomLGFX.open/1` とポート専用機能を利用できない
- ポートソースを削除する時期は、NIF の機能範囲と利用側の移行状況に依存する

## 採用しなかった代替案

### ポート実装を直ちに削除する

NIF の単純さと性能には合うが、実行時設定、タッチ、スプライト、パレット、JPEG を使う
既存アプリケーションを失うため採用しない。

### NIF をポートの翻訳単位へ含め続ける

ポート専用コードをリンクせず NIF だけを構築できないため採用しない。

### ポートを常に構築する

互換性は単純になるが、NIF だけを使うファームウェアでも不要なコードとフラッシュ使用が
残るため採用しない。

## 今後への影響

新しい一般向け機能は、長時間 AtomVM のスケジューラーを占有しない同期処理である限り、
まず `LGFX` NIF へ追加する。ポートを完全に削除する前に、残る機能差、下流利用、実機検証を
明示的に見直す。
